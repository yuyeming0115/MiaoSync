# MiaoSync 项目缺陷与优化分析报告

> 分析日期：2026-08-13（修复验收：2026-10-10）
> 分析范围：当前工作区源码、配置、文档、测试与构建脚本
> 项目版本状态：`main` 分支，远端跟踪分支已恢复（origin/main 可达）
> 结论性质：静态审查 + 本地构建/测试验证；未对真实用户数据目录执行同步
>
> **修复进度（2026-10-10）**：P0-1 ~ P0-4、P1-1 ~ P1-8 已全部实现并通过验收（详见文末变更记录「可信内核里程碑」）。本报告保留作为缺陷定义与验收依据的档案。

## 1. 执行摘要

MiaoSync 已具备一个 MVP 的完整外形：Go 单二进制、内置 Web GUI、双向/备份模式、快照、冲突副本、危险删除确认、模拟器与基础测试均已落地。当前源码可以通过：

- `go test ./...`
- `go test -race ./...`
- `go vet ./...`
- `go build ./...`

但项目目前**不适合直接承载唯一副本或高价值数据**。核心原因不是功能缺失，而是同步引擎的状态机、失败恢复和写入原子性尚未达到备份工具应有的数据安全标准。

综合评估：

| 维度 | 评分 | 结论 |
|---|---:|---|
| 功能完整度 | 7/10 | MVP 主流程齐全，界面与报告体验已有基础 |
| 数据安全 | 3/10 | 存在删除规划冲突、失败后错误快照、非原子覆盖等高风险问题 |
| 正确性 | 4/10 | 两节点基础场景可用，多节点、删除、角色语义仍不可靠 |
| 性能 | 4/10 | 每次、每对节点重复全量 SHA-256，目录越大退化越明显 |
| 可维护性 | 6/10 | 分层清楚，但引擎职责过重，格式、文档和实现有偏差 |
| 测试保障 | 4/10 | 仅同步引擎 4 个基础测试，关键破坏性路径没有覆盖 |
| 发布成熟度 | 4/10 | 可构建，但缺少 CI、版本化迁移、发布校验和故障恢复设计 |

建议将下一阶段目标从“增加功能”调整为“建立可信同步内核”，优先完成 P0 数据安全修复，再考虑自动触发、加密或断点续传。

## 2. 项目概览

### 2.1 当前结构

| 模块 | 主要职责 | 状态 |
|---|---|---|
| `cmd/miaosync` | 程序入口、日志、浏览器启动 | 可用 |
| `internal/sync` | 扫描、hash、计划、执行、快照 | 核心风险集中区 |

### 2.2 已验证事实

- Go 版本声明为 `1.22`，仅一个直接依赖 `gopkg.in/yaml.v3`，供应链面较小。
- 当前单元测试全部通过，竞态检测也通过；但竞态测试没有覆盖 Web 服务并发请求。
- `gofmt -l cmd internal` 返回 4 个未格式化文件：`internal/sync/snapshot.go`、`internal/sync/types.go`、`internal/web/api.go`、`internal/web/server.go`。

- 工作区根目录存在多个历史 `.exe` 和本地报告，虽被忽略但增加误用旧版本的概率。

## 3. 缺陷清单

### P0-1：删除场景会同时生成“恢复复制”和“同步删除”

**位置**：`internal/sync/engine.go:94-141`

规划器先按“某端独有文件”生成复制动作，然后又根据快照生成删除动作。例如源端删除、目标端未修改时：

1. `sNow == nil && dNow != nil` 在 mirror 模式先生成 `dst -> src` 复制；
2. 随后的删除检测又生成删除 `dst` 的动作；
3. 执行后可能变成源端恢复、目标端删除，而不是两端都删除。

这会使一次运行结束后两个节点仍不一致，并可能在下一轮继续反向传播。动作顺序还依赖当前生成过程，缺少显式的互斥和拓扑排序。

**建议**：将每个路径先归类为一个完整状态转换，再只生成一个确定结果。不能把“独有文件补齐”和“删除传播”作为两个互不知情的后处理阶段。推荐建立 `PathDecision`，明确 `unchanged / created / modified / deleted` 的双端组合矩阵。

**验收用例**：首次同步完成后，在任一端删除文件；再次 mirror 同步应只产生一个删除动作，最终两端都不存在该文件。

### P0-2：动作失败后仍保存快照，会把失败状态当作成功基线

**位置**：`internal/sync/engine.go:235-253`、`internal/sync/engine.go:282-321`

`Apply` 遇到单文件失败只累计 `summary.Errors`，仍返回 `nil error`。`Run` 随后无条件重新扫描并保存两端快照。后果包括：

- 失败或截断的目标文件被写入“成功快照”；
- 下一次运行可能把截断文件视为正常变更或冲突；
- 若截断文件 mtime 更新更晚，冲突策略可能反向覆盖正确源文件；
- 用户看到“同步完成，但有错误”，系统内部却失去可靠的上次成功基线。

**建议**：只有整次事务达到提交条件时才更新快照。至少应做到：任何 copy/delete/conflict 失败时不提交相关节点快照；更稳妥的是记录 run journal，逐动作校验成功后一次提交快照。

### P0-3：复制与冲突处理不是原子操作，失败可直接破坏原文件

**位置**：`internal/sync/engine.go:340-357`、`internal/sync/engine.go:360-385`

`copyFile` 使用 `os.Create(to)`，目标文件会先被截断，再开始复制；进程退出、磁盘拔出、空间不足或 I/O 错误都会留下半文件。`ConflictNewer` 更危险：先 `os.Remove(loserPath)`，再复制胜方，一旦复制失败，败方原件已丢失。`ConflictRename` 先移动旧文件再复制，虽然保留副本，但原路径仍可能缺失。

**建议**：统一采用“同目录临时文件 -> 流式复制 -> `Sync` -> hash/size 校验 -> 保留权限和 mtime -> 原子 rename”的写入协议。替换已有文件时先生成可恢复备份或使用平台适配的 replace；任何失败必须清理临时文件并保留原目标。

### P0-4：没有全局运行锁，多请求可并发修改同一批文件和快照

**位置**：`internal/web/api.go:55-73`、`internal/web/api.go:170-217`、`internal/web/server.go:15-19`

Go HTTP 服务会并发处理请求，但 `Server` 没有 mutex、运行状态或任务队列。不同浏览器标签页可以同时发起同步，也可在同步时保存配置。多个同步会同时扫描、覆盖、删除和写同一个 `snapshot.json.tmp`。

竞态测试当前通过并不能证明安全，因为测试没有启动 Web 服务或并发调用 handler。

**建议**：服务层增加单实例任务管理器；同一时间只允许一个执行任务。配置读取使用不可变快照或 `RWMutex`，保存配置时拒绝/排队。接口返回明确的 `409 Conflict` 和当前任务信息。

### P1-1：`backup` 方向由节点数组顺序决定，`role` 字段实际未生效

**位置**：`internal/sync/engine.go:193-199`、`internal/sync/types.go:33-38`、`internal/config/config.go:21-26`

代码虽然允许 `peer/source/target`，但规划与执行完全不读取 `Role`。backup 模式只把每个 pair 的前者当 source、后者当 target。三节点时执行方向为 `A -> B`、`A -> C`、`B -> C`，语义取决于配置/选择顺序，而不是角色。

**建议**：明确备份拓扑。最简单的模型是 backup 模式必须恰好一个 `source`、一个或多个 `target`，只生成 `source -> target`；mirror 模式只允许 `peer`。非法组合应拒绝保存和执行。

### P1-2：预览、危险确认和执行不是同一份计划，存在 TOCTOU

**位置**：`internal/web/api.go:139-167`、`internal/web/api.go:170-217`

预览返回动作，但执行时重新扫描并重新规划；危险确认再次请求时又重新规划。期间文件可能变化、硬盘可能重新挂载，用户确认的并不是实际执行的动作集合。

**建议**：预览生成带 ID、节点身份、根路径指纹、快照版本和过期时间的不可变计划。执行时校验前置状态；任何文件状态变化都让计划失效并要求重新预览。

### P1-3：节点路径未检查重复、嵌套或根目录风险

**位置**：`internal/config/config.go:53-82`

配置只检查节点名称和非空路径，没有阻止：

- 两节点解析到同一目录；
- 一个节点是另一个节点的子目录；
- 同一目录通过大小写、相对路径、符号链接得到不同写法；
- 误选盘符根目录或用户主目录等超大范围。

嵌套目录可能造成递归复制和目录指数膨胀，是直接的数据与容量风险。

**建议**：使用 `Abs + Clean + EvalSymlinks` 生成 canonical path，拒绝相同/祖先后代关系；对根目录、高风险系统目录做显式二次确认。

### P1-4：符号链接行为与设计文档不一致，可能读取同步根目录之外的数据

**位置**：`internal/sync/engine.go:29-68`、`docs/design.md`

`WalkDir` 遇到符号链接时不会进入目录，但当前逻辑会把链接当普通文件并调用 `os.Open` 计算 hash，实际读取其目标内容。复制时也会把目标内容复制成普通文件。若链接指向根目录外，扫描会越过用户选择的边界。

**建议**：用 `DirEntry.Type()&os.ModeSymlink` 明确识别。MVP 可直接跳过并报告；后续若支持链接，应保存链接本身且校验目标不越界。

### P1-5：大小写折叠会静默吞掉冲突文件

**位置**：`internal/fs/plat.go:13-15`、`internal/sync/engine.go:62-67`

所有平台都用小写路径作为 map key。在区分大小写的文件系统上，`A.txt` 与 `a.txt` 会落到同一个 key，后扫描者覆盖前者，且没有警告。同步到 Windows/exFAT 时也没有明确的冲突迁移策略。

**建议**：扫描阶段检测 compare key 冲突并阻止执行，向用户列出冲突路径；不要静默覆盖状态表。比较规则应由目标文件系统能力决定，而不是全局固定。

### P1-6：默认忽略规则不包含冲突副本，副本会继续传播

**位置**：`internal/config/config.go:109-115`、`internal/sync/engine.go:363-366`

引擎生成 `*.conflict-<timestamp>.*`，默认 ignore 却没有 `*.conflict-*`。模拟器手工加入该规则，说明开发者已经遇到传播问题，但正式默认配置没有同步处理。三节点时冲突副本可能被复制到其他节点，并进入后续快照。

**建议**：把冲突文件放入专用 `.miaosync/conflicts/<run-id>/`，不要混在业务目录；若保持现状，至少默认忽略并在 GUI 提供冲突中心。

### P1-7：每个 pair 都全量读取并 hash，三节点一次执行会重复扫描很多次

**位置**：`internal/sync/engine.go:18-74`、`internal/sync/engine.go:169-186`、`internal/sync/engine.go:388-399`

扫描对每个文件无条件计算 SHA-256。三节点预览对 3 个 pair 扫描 6 次；执行又扫描 6 次，且每个 pair 完成后保存快照再扫描 6 次。也就是说，一次“预览 + 执行”最多对每个节点重复读取多轮，大文件目录会被磁盘吞吐完全限制。

**建议**：一次运行每节点只扫描一次，并缓存结果；应用动作后在内存更新状态，最后每节点写一次快照。后续可用 `size + mtime + file-id` 快速路径，仅疑似变化时重新 hash；最终复制后仍需目标 hash 校验。

### P1-8：快照缺少版本、节点身份和恢复信息

**位置**：`internal/sync/snapshot.go:14-56`

快照只有节点名、更新时间与文件表，没有 schema version、设备/卷标识、根目录指纹、同步组 ID、成功 run ID 或校验和。移动硬盘盘符复用、目录复制、格式升级或损坏时难以判断快照是否属于当前节点。

**建议**：引入版本化元数据和 journal；校验卷/目录身份；损坏时进入只读诊断而不是直接覆盖。Windows 上需验证 `os.Rename` 覆盖已有 snapshot 的行为并实现可靠 replace。

### P2-1：配置加载不执行完整校验，非法枚举被静默纠正

**位置**：`internal/config/config.go:53-89`、`internal/sync/types.go:101-120`

启动时 `Load` 只补默认值，不调用 `Validate`。非法 mode/conflict 在 API 执行时静默回退为 `mirror/rename`，可能把用户预期的安全模式变成双向同步。角色值也没有枚举校验。

**建议**：启动、保存、执行三处统一走严格验证；未知值返回错误，不做安全语义上的隐式回退。

### P2-2：HTTP 服务缺少方法约束、大小限制、超时和优雅关闭

**位置**：`internal/web/server.go:46-47`、`internal/web/api.go`

部分 handler 不检查 HTTP method；JSON body 未使用 `MaxBytesReader`；直接使用 `http.ListenAndServe`，没有 `ReadHeaderTimeout`、`IdleTimeout`、`WriteTimeout` 或 shutdown。当前只监听 localhost 降低了外部攻击面，但无法防止本机异常请求拖住进程。

### P2-3：复制后不保留 mtime/权限，也不校验 hash

**位置**：`internal/sync/engine.go:340-357`

复制只传输字节，不保留 mtime 和权限。冲突胜负依赖 mtime，却又由同步操作改变 mtime；多设备时还受时钟漂移影响。文档已把“复制后 hash 校验”列为规划项，但对同步工具而言应提升为正确性基础设施。

### P2-4：测试覆盖与项目风险不匹配

**位置**：`internal/sync/engine_test.go`

现有测试覆盖首次 mirror、基础 backup、rename 冲突和 ignore，缺少：

- 删除传播与修改/删除冲突；
- 三节点和节点顺序；
- 三种冲突策略完整行为；
- 危险删除阈值和确认后状态变化；
- 磁盘满、权限拒绝、中途失败、进程中断；
- 同步并发、配置并发和 SSE 断连；
- 符号链接、大小写冲突、嵌套路径、Unicode 归一化；
- 大文件、零字节文件、同秒时间戳、快照损坏与升级。

### P2-5：文档、注释和实现存在漂移

典型例子：

- `types.go` 注释写内容 hash 为 `blake2b`，实现实际是 SHA-256；
- 设计文档称快照用于“避免全量扫描”，实现每次仍全量读取所有文件；
- 设计说明符号链接应忽略/展开，当前实现没有显式策略；
- README 把 role 描述为业务语义，但执行层未使用。

建议把可验证行为写成测试和 ADR，文档只引用已兑现能力。

### P3：工程化与体验优化项

- 增加 CI：`gofmt -l`、`go vet`、`go test -race`、跨平台 build、静态检查。
- 清理根目录历史二进制的使用方式，以 `dist/<version>/` 和构建清单避免运行错版本。
- 配置保存改为原子写并保留 `.bak`，页面显示实际加载配置路径与版本。
- 日志增加 run ID、节点、动作 ID、错误码，并支持导出脱敏诊断包。
- 状态扫描应复用引擎扫描结果并显示错误，而不是吞掉 `WalkDir` 错误后给出不完整计数。
- 前端增加取消、正在运行状态、断连恢复和计划过期提示。

## 4. 推荐重构方案

### 4.1 同步状态机

建议把当前 `Scan -> Plan pair -> Apply -> Save pair snapshot` 改成：

```text
获取独占运行锁
  -> 固化配置与节点 canonical path
  -> 每节点扫描一次
  -> 校验路径、卷身份、大小写冲突、符号链接
  -> 基于上次“成功提交快照”生成全局计划
  -> 持久化 plan + run journal
  -> 用户确认同一 plan ID
  -> 原子执行动作并逐项校验
  -> 全局一致性复验
  -> 一次提交所有节点快照
  -> 释放锁并输出报告
```

关键原则：

1. 一个相对路径只能得到一个最终决策。
2. 计划必须可重放、可审计，并绑定前置状态。
3. 文件写入必须原子；失败不得破坏旧文件。
4. 只有一致性复验成功后才能推进成功快照。
5. 多节点计划必须全局计算，不能把两两同步简单串联当作全局一致性。

### 4.2 建议拆分

| 新组件 | 职责 |
|---|---|
| `Scanner` | 单次扫描、文件系统能力检测、碰撞/链接报告 |
| `Planner` | 纯函数式状态矩阵，输出不可变全局计划 |
| `Executor` | 原子复制、删除隔离、校验、取消、进度 |
| `SnapshotStore` | 版本化快照、journal、提交/恢复 |
| `RunManager` | 独占锁、任务状态、计划 ID、并发控制 |
| `Topology` | mirror/backup 角色与方向校验 |

## 5. 分阶段落地路线

### 阶段 A：数据安全止血（P0，建议先完成）

1. 重写删除状态矩阵，补齐删除回归测试。
2. 复制改为临时文件 + 校验 + 原子替换。
3. 任一动作失败时禁止提交快照。
4. 引入同步独占锁，禁止并发执行与执行中改配置。
5. 校验相同/嵌套路径、符号链接和大小写碰撞。

**退出标准**：故障注入下不会丢失原文件；删除、失败恢复、并发用例全部通过。

### 阶段 B：语义收敛（P1）

1. 实现角色驱动的 backup 拓扑。
2. 使用不可变 plan ID 串联预览、确认和执行。
3. 冲突副本移入 `.miaosync/conflicts`。
4. 建立版本化快照和 run journal。
5. 完成三节点全局规划，移除 pairwise 串行副作用。

**退出标准**：任意节点顺序得到相同结果；重复执行幂等；计划变化必须重新确认。

### 阶段 C：性能与可观测性（P1/P2）

1. 每节点每轮只扫描一次。
2. 增加 metadata 快速路径和 hash 缓存。
3. 增加 context 取消、速率/剩余时间、结构化日志。
4. 增加大目录 benchmark 与真实 exFAT/NTFS/APFS 验证矩阵。

### 阶段 D：发布工程化（P2/P3）

1. CI、跨平台产物校验、版本注入与 checksum。
2. 配置/快照迁移工具和兼容策略。
3. 故障诊断包、发布说明、回滚说明。
4. 完成后再排期加密、插盘触发和断点续传。

## 6. 建议的验收指标

| 指标 | 目标 |
|---|---|
| 数据完整性 | 所有成功 copy 的目标 SHA-256 与源一致 |
| 原子性 | 任意时刻强制终止，旧目标或新目标至少一个完整可用 |
| 快照一致性 | 只有全局复验成功的 run 才能成为新基线 |
| 幂等性 | 成功同步后立即再次规划，动作数为 0 |
| 顺序无关性 | mirror 多节点结果不受节点选择顺序影响 |
| 故障恢复 | 磁盘满、拔盘、权限失败后再次运行不反向污染正确副本 |
| 性能 | 一次 run 每节点最多一次全量扫描；未变化文件不重复读取内容 |
| 并发 | 第二个同步请求稳定返回 409，不进入引擎 |

## 8. 结论

MiaoSync 的产品方向和工程骨架是合理的，继续在现有 Go 单二进制架构上演进没有明显障碍。真正需要重做的是同步核心的事务边界：当前实现把“扫描、两两规划、逐项执行、快照提交”串在一起，但缺少单路径决策、原子写、失败回滚和全局提交。

建议暂停新增大功能，用一个里程碑完成 P0 与关键 P1。完成后，项目才能从“可演示 MVP”提升为“可放心用于真实数据的工具”。在此之前，应明确提示用户：只对有额外备份的数据使用，并始终先预览。
